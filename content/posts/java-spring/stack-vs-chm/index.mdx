## 들어가며
stack은 쓰지 마라고 하고 concurrent 해시맵(이하 CHM)은 권장하는 듯한 뉘앙스를 볼 수 있다. 둘다 같은 동기화 처리가 되는 JCF 인데 어째서 다르게 받아들이는가?

이들 각자는 스레드의 동기화를 위해 stack 메소드 방식, CHM은 싱크로나이즈 블록을 사용한다. 스택의 구현을 보면 모든 메소드에 synchronized 키워드가 붙어있다. 이와 다르게 CHM의 구현을 보면 특정 구간에 synchronized 을 만들어서 처리한다. 이것이 사용을 권장하거나 권장하지 않는 이유라면 이 차이가 무엇을 의미하나.


## Stack의 synchronized 방식
메소드별로 락을 건다는 것은 메소드 이 후에 락이 풀리는 것을 의미한다. 따라서 스택이 비었는지 확인하고, 거기서 `push`, `pop`을 하는 것은 하나의 락에서 처리되는 것이 아니고 각자 처리되게 된다. synchronized를 메소드에 넣으면 인스턴스가 락의 대상이 되므로 인스턴스가 잠기긴 하지만, 개별 메소드가 처리되는 사이에 락은 해제되게 된다. 따라서 synchronized가 스택에 선언되어 있음에도 불구하고 스택 변수가 비어있음을 확인하고 빼내는 코드는 멀티스레드 환경에서 충분히 오류가 발생할 수 있다. 

아래 코드와 표를 참고해보자. 
```java
Stack<Item> stk = new Stack<>();

if(!stk.isEmpty()) {
	stk.push(new Item());
}
```

위와 같은 코드에서 `stk`의 크기가 스레드 A가 최초 진입한 시점에 1이라고 가정하자. 그럼 스레드가 각각 t1 ~ t3 의 시간 사이에 락을 걸었다가 풀게 되므로 각 연산 사이에 막히는 구간이 없이 실행된다.

| 시각  | 스레드 A                                | 스레드 B                              | stk.size() |
| --- | ------------------------------------ | ---------------------------------- | ---------- |
| t1  | `isEmpty()` -> `false`, 순간 락이 걸렸다 풀림 | 락 대기                               | 1          |
| t2  | 락 대기                                 | `stk.pop()`, 락이 없는 상태이므로 `pop`이 가능 | 0          |
| t3  | `stk.pop()` -> `EmptyStackException` |                                    | 0          |



## CHM의 synchronized 방식
CHM은 synchronized 블록을 쓴다고 했다. CHM의 경우 내부적으로 hash의 값마다 버킷을 만들고 버킷의 배열로 원소를 저장한다. synchronized 블록에 가는 케이스는 버킷에 노드가 존재하는 경우인데, 이때 락을 거는 대상은 버킷의 첫번째 노드이다. 아래는 `remove`(삭제 메소드)의 실제 구현을 단순화한 코드이다.

```java
// CHM.remove를 단순화 한 의사 코드
public V remove(Object key) {
    int i = getIndex(key);

    // 1. [스핀 루프] 작업이 완료될 때까지 계속 재시도
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f = tabAt(tab, i); // 버킷의 현재 Head 읽기 (Volatile Read)

        if (f == null) {
            return null; // 삭제할 대상 없음 (락 없이 즉시 종료)
        }

        // 2. [세분화된 락] 전체 테이블이 아닌, 해당 버킷의 Head(f)에만 락을 검
        synchronized (f) {

            // 3. [이중 검증] 락을 얻는 대기 시간 동안 Head가 바뀌지 않았는가?
            if (tabAt(tab, i) == f) {
                
                // Head 노드 자체가 삭제 대상인 경우
                if (isTarget(f, key)) {
                    setTabAt(tab, i, f.next); // 배열의 Head를 다음 노드로 교체
                    return f.val;              // 성공! 루프 탈출
                }

                // 연결 리스트 내부 노드가 삭제 대상인 경우
                for (Node<K,V> prev = f, e = f.next; e != null; prev = e, e = e.next) {
                    if (isTarget(e, key)) {
                        prev.next = e.next;   // 리스트에서 e 노드 제거
                        return e.val;          // 성공! 루프 탈출
                    }
                }

                return null; // 리스트 끝까지 찾았으나 대상 없음
            }
        }
        // 4. [검증 실패 시] 락을 얻었더니 Head가 바뀌었다면(tabAt != f)
        // 아무것도 하지 않고 for 루프의 처음으로 돌아가 변경된 최신 Head로 다시 시도!
    }
}
```

락을 거는 대상이 버킷의 첫 노드라는 것은 다른 버킷에 락을 걸지 않는 다는 의미이다. 따라서 락의 경계 자체가 지엽적이다. 버킷이 비어 있는 경우는 아예 락을 걸지도 않는다.

## Stack과 CHM의 동기화 방식 차이
만약 stack 처럼 메소드 단위 락을 걸었다면 기타 삽입이나 조회 연산에도 락이 걸리면서 더 많은 비용(성능 하락 등)을 지불해야 했을 것이다. 더군다나 위의 `stack` 코드에서 나온 형식의 `if(check) { act }` 와 같은 구조를 쓰지 않고 자체적으로 `computeIfAbsent` 와 같은 메서드를 제공한다. 이런 요소들 때문에 멀티스레드 간 스레드 세이프가 필요한 로직에 CHM은 에 권장되나, 스택의 사용은 권장하지 않는 것이다.


## 원자성과 독립성
중요한 것은 synchronized 를 메소드에 썼느냐, 블록으로 선언 했느냐가 아니다. 삭제나 삽입 연산이 원자성을 갖느냐 갖지 못하느냐가 중요한 것이다. (데이터베이스의 트랜잭션의 성질에서 말하는 그 원자성(Atomicity)을 말한다. 트랜잭션이 다 되던지 안되던지를 보장해야 하고 각 트랜잭션이 독립적으로 처리되어야 한다.) 이와 유사하게 자료구조의 삽입/삭제 연산의 원자성, 독립성이 보장되는 것이 CHM 이고, 보장되지 않는 것이 스택인 것이다.

## 마치며
JCF를 들여다 볼 때마다 느끼지만 쉬운 접근성 때문에 사용하는 것에 비해 그 내부 설계에 대해 배울점이 많은 재료 같다. CAS 는 낙관적 락과 유사해 보이고, 싱크로나이즈드는 비관적 락과도 유사해 보인다. 동기화를 위해서 어떻게 처리해야 할지 각각 큰 컨셉의 락을 어떻게 해볼 수 있다 등을 배울 수 있는 것 같다.
