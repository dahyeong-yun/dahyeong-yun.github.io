지난번 [[custom-logging-for-learn-slf4j|SLF4J 구현체를 직접 만들어 보며 로깅 라이브러리의 구조를 뜯어보았을 때]], 유독 눈에 밟히던 메서드가 하나 있었다. 바로 `SLF4JServiceProvider` 인터페이스의 `getMDCAdapter()`였다.

당시에는 *"로그에 컨텍스트 정보를 추가하는 역할을 한다는데 아직 깊게 써보지 못했다"* 하고 가볍게 넘겼지만, 실무에서 동시 요청이 쏟아지는 분산 환경을 다루다 보면 결국 이 **MDC(Mapped Diagnostic Context)**를 마주하지 않고는 배길 수가 없다.

그런데 MDC의 내부를 파고들면 파고들수록 한 가지 강렬한 의문이 머릿속을 떠나지 않았다.

> *"MDC는 왜 하필 그 위험천만한 `ThreadLocal`을 기반으로 만들어졌을까? 스레드 풀에서 자칫 잘못하면 다른 사람의 정보가 노출되고 메모리가 새는데, 왜 설계자들은 이런 위험을 감수했을까?"*

이 의문을 풀기 위해 20년 전의 역사적 배경과 최근 Java 언어 설계자들의 공식적인 반성까지 거슬러 올라가 보았다.

---

## 1. 일꾼의 비밀 주머니: ThreadLocal의 달콤한 유혹

웹 애플리케이션에서 수많은 사용자의 로그가 뒤섞이지 않게 하려면 모든 로그마다 `traceId`나 `userId`를 남겨야 한다.

만약 MDC가 없었다면 우리는 어떻게 코드를 짰을까?
```java
// ThreadLocal이 없던 시절의 비극 (파라미터 드릴링)
public void createOrder(OrderRequest req, String traceId) {
    log.info("[{}] 주문 생성 시작", traceId);
    paymentService.pay(req, traceId);
}

public void pay(OrderRequest req, String traceId) {
    log.info("[{}] 결제 처리 중", traceId);
    pgClient.call(req, traceId);
}
```
비즈니스 로직과 아무 상관도 없는 인프라성 추적 ID 하나 때문에 컨트롤러부터 서비스, 레포지토리, 외부 통신 모듈까지 모든 메서드의 시그니처가 지저분하게 오염된다.

이때 구원투수로 등장한 것이 바로 **[[threadlocal|ThreadLocal]]**이었다.
식당에서 일하는 직원(Thread)의 앞치마에 달린 **‘개인 주머니’**처럼, 그 스레드가 살아있는 동안에만 자기 혼자 몰래 꺼내 쓸 수 있는 독립된 보관함이다.

1. 요청이 들어오는 길목(Filter)에서 직원의 주머니에 쪽지를 쏙 넣는다: `MDC.put("traceId", id)`
2. 이후 어떤 서비스, 어떤 메서드에서 `log.info()`를 호출하든 로깅 엔진이 그 주머니를 뒤져 자동으로 로그 앞에 `[traceId]`를 붙여준다.
3. 비즈니스 코드는 단 1%도 수정할 필요가 없었다.

동기화 락(Lock)도 필요 없어 속도는 O(1)로 빨랐고, 코드는 완벽하게 우아해졌다.

---

## 2. 대기실이 생기자 닥쳐온 재앙: 스레드 풀 오염

하지만 행복은 오래가지 않았다. 성능을 위해 스레드를 쓰고 버리는 대신 **[[thread-pool|스레드 풀(Thread Pool)]]**에 모아두고 재사용하기 시작하면서부터다.

직원이 손님 A를 응대하고 퇴근(스레드 파괴)하면 주머니 속 쪽지도 함께 버려지니 안전했다. 하지만 스레드 풀 환경에서는 직원이 해고되지 않고 대기실로 돌아간다.

```
[1번 스레드] 손님 A 주문 처리 중 주머니에 "A의 카드번호" 보관
      ↓ (요청 종료... 그러나 깜빡하고 주머니를 비우지 않음!)
[1번 스레드] 대기실(스레드 풀)로 복귀
      ↓ (잠시 후)
[1번 스레드] 손님 B의 요청에 다시 배정됨!
      ↓
[1번 스레드] 손님 B의 로그를 찍는데, 주머니에 남아있던 "A의 카드번호"가 출력됨! 💥
```

실제로 필터의 `finally` 블록에서 `MDC.clear()`를 단 한 줄 빼먹었을 뿐인데, **다음 사용자의 로그에 이전 사용자의 ID와 민감한 주문 내역이 찍히는 심각한 보안 사고**와, 스레드가 죽지 않아 메모리가 계속 차오르는 **메모리 누수(OOM)**가 빈번하게 발생했다.

---

## 3. 그럼 애초에 왜 ThreadLocal을 선택했을까?

이렇게 위험한데, Log4j와 Logback의 창시자인 세키 궬쥐(Ceki Gülcü)는 왜 굳이 `ThreadLocal`을 선택했을까?

답은 **"당시의 시대적 배경에서는 이것이 가장 완벽하고 천재적인 타협안이었기 때문"**이다.

### 1) 절대적이었던 'Thread-per-Request' 패러다임
2000년대 초반(Log4j 1.x 시절)은 서블릿(Servlet)의 시대였다.  
비동기 논블로킹(`@Async`, `CompletableFuture`)이나 리액티브(WebFlux) 같은 개념은 아예 없었다.
브라우저에서 요청이 들어오면 톰캣 스레드 딱 1개가 배정되어, DB를 조회하고 HTML을 렌더링해서 내보낼 때까지 혼자서 끝까지 동기식으로 처리했다.

즉, **"스레드 1개 = 1개의 HTTP 요청"**이라는 등식이 100% 성립하던 시절이었다. 그러니 "스레드에 데이터를 묶어둔다"는 발상은 너무나 자연스럽고 합리적인 접근이었다.

### 2) "finally 한 줄이면 충분하다"는 믿음
당시의 단순한 동기식 서블릿 환경에서는 `Filter`의 `try-finally` 블록 하나만으로 스레드 풀 오염을 완벽하게 통제할 수 있었다.
```java
try {
    MDC.put("traceId", id);
    chain.doFilter(request, response);
} finally {
    MDC.clear(); // "이거 한 줄이면 되는데 뭐가 문제야?"
}
```
설계자들의 눈에는 약간의 주의사항만 지키면 **"메서드 파라미터 오염 0% + 락 없는 극강의 성능"**을 누릴 수 있는 압도적인 가성비의 선택지였던 것이다.

## 4. 20년 뒤, 폭탄이 되어 돌아온 기술 부채

하지만 20년이 흐른 지금, 웹 생태계는 완전히 뒤바뀌었다.
* 단일 요청 안에서도 `@Async`로 별도 스레드를 띄우고,
* 수천 개의 비동기 파이프라인이 쪼개져 실행되며,
* WebFlux처럼 단일 스레드가 수많은 요청의 조각들을 번갈아 가며 처리하는 시대가 되었다.

`Thread-per-Request` 공식이 깨지자, `finally { MDC.clear(); }`라는 단순한 방어벽은 무너져 내렸다. 비동기 스레드로 넘어가면 MDC가 뚝 끊겼고, 리액티브에서는 엉뚱한 요청의 컨텍스트를 읽었다.

결국 Java 언어 자체를 설계하는 OpenJDK의 거두들(Brian Goetz, Ron Pressler)까지 나섰다. 그들은 Java 21 공식 스펙인 **[JEP 446 (Scoped Values)](https://openjdk.org/jeps/446)**에서 `ThreadLocal`의 설계를 강도 높게 지적했다.

> *"ThreadLocal 변수에는 치명적인 설계 결함이 있다. 한번 쓰여진 데이터는 명시적으로 지우지 않는 한 스레드 수명 내내 남아있으며, **스레드 풀 환경에서는 이것이 필연적으로 메모리 누수와 작업 간 컨텍스트 오염을 유발한다.**"*

## 5. 마치며: 우리는 어디로 가고 있는가?

돌이켜보면 MDC가 `ThreadLocal`을 택했던 것은 당대로서는 최선의 엔지니어링 타협이었다. 하지만 환경이 변하면서 그 우아했던 선택은 현대 개발자들에게 가장 까다로운 관리 포인트(기술 부채)가 되었다.

다행히 오늘날의 우리는 더 이상 이 위험을 맨몸으로 견딜 필요가 없다.
1. Spring Boot 3의 **[[distributed-tracing-context-propagation|Micrometer Tracing]]**은 개발자가 수동으로 MDC를 끄고 켜는 수고를 프레임워크 뒤로 완전히 감춰버렸다 (자율주행처럼 알아서 비동기 전파와 정리를 수행한다).
2. Java 최신 표준인 **Scoped Values**는 불변성과 스코프 범위를 강제하여 `clear()` 누락으로 인한 스레드 오염을 언어 차원에서 원천 봉쇄하기 시작했다.

기술의 역사를 이해하고 나면, 프레임워크가 제공하는 '편리한 마법' 뒤에 도사린 트레이드오프가 비로소 보인다. 혹시 지금 작성 중인 코드 어딘가에 `MDC.put`을 호출해 두고 `finally` 블록을 빠뜨린 곳은 없는지, 한 번쯤 점검해 볼 일이다.
