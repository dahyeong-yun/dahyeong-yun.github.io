## 들어가며: 3배 차이의 미스터리

"오프셋(Offset) 페이징은 데이터가 많아질수록 느리고, 커서(Cursor) 페이징은 항상 빠르다."

백엔드 개발자라면 누구나 한 번쯤 들어봤을 기술 상식이다. 이론은 명쾌하다. 오프셋 방식은 앞선 행들을 메모리에서 일일이 읽어 버려야($O(\text{offset} + \text{limit})$) 하지만, 커서 방식은 인덱스를 타고 즉시 필요한 위치로 수직 점프($O(\text{limit})$)하기 때문이다.

실제로 이를 눈으로 확인해 보고 싶어, H2 데이터베이스에 **20,000건의 더미 데이터를 적재하고 1,000번째 페이지(마지막 20건)를 조회하는 성능 벤치마크 테스트**를 작성했다.

그런데 기이한 현상이 벌어졌다.

어떤 환경(CI/가상 격리 환경)에서는 오프셋과 커서의 소요 시간이 거의 차이가 나지 않거나 심지어 오프셋이 미세하게 빠르게 측정되기도 했는데, 내 로컬 머신에서 직접 실행해 보니 **커서 방식이 오프셋보다 정확히 3배(3x) 빠르게 측정**된 것이다.

> *"똑같은 20,000건 데이터이고, 똑같은 쿼리인데 왜 실행하는 환경과 시점에 따라 결과가 이렇게 널뛰기를 할까?"*

이 의문을 파고들면서, 단위 테스트 환경에서 흔히 사용하는 **인메모리 DB(H2) 마이크로 벤치마크의 치명적인 함정**을 마주하게 되었다.

---

## 1. 함정의 시작: 수십 마이크로초(µs)의 세계

로그에 찍힌 실제 측정 시간을 자세히 들여다보았을 때 실마리가 풀리기 시작했다.

- 오프셋 방식 소요 시간: `0.08ms` (약 80µs)
- 커서 방식 소요 시간: `0.02ms` (약 20µs)

수치상으로는 분명 **"3배 빠르다"**가 맞다. 하지만 절대적인 시간을 보면 **불과 0.06밀리초(60마이크로초)의 차이**였다. 1밀리초도 안 되는 찰나의 시간이다.

이 정도로 미세한 시간대에서는 데이터베이스 엔진의 순수한 쿼리 처리 비용보다, **JVM 런타임의 온갖 노이즈**가 측정값을 좌우한다.

### ① JVM JIT 컴파일러의 웜업(Warm-up) 상태
자바 코드는 처음 실행될 때 인터프리터 방식으로 해석되다가, 반복 호출되는 루프를 감지하면 C1/C2 JIT 컴파일러가 네이티브 기계어로 최적화(컴파일)한다.
테스트 메서드가 실행되는 첫 1~2회에는 JIT 웜업이 덜 된 상태라 인터프리터 오버헤드가 크고, 웜업이 끝난 뒤에는 극도로 빨라진다. 테스트 실행 순서나 반복 횟수에 따라 측정값이 수배씩 요동치는 첫 번째 이유다.

### ② PreparedStatement 파라미터 바인딩 비용
- 오프셋 쿼리: `WHERE user_id = ? ORDER BY id ASC LIMIT ? OFFSET ?` (파라미터 3개)
- 커서 쿼리: `WHERE user_id = ? AND id > ? ORDER BY id ASC LIMIT ?` (파라미터 3개)

마이크로초 단위의 세계에서는 JDBC 드라이버가 파라미터 객체를 생성하고 네트워크/메모리 소켓에 바인딩하는 CPU 클럭 수마저 유의미한 비율을 차지한다.

### ③ Minor GC와 CPU 스케줄링 노이즈
2만 건의 데이터를 힙 메모리에 벌크 INSERT하고 쿼리 객체를 생성하는 과정에서 순간적으로 가비지 컬렉션(GC)의 미세한 Stop-the-World가 끼어들거나, OS의 CPU 코어 쓰로틀링(Turbo Boost)이 발생하면 0.05ms 정도는 순식간에 튈 수밖에 없다.

## 2. 결정적 괴리: 인메모리 DB에는 "디스크"가 없다

하지만 가장 본질적인 이유는 따로 있었다. 바로 **H2 인메모리 DB의 물리적 한계**다.

실무에서 사용하는 디스크 기반 RDBMS(MySQL InnoDB 등)에서 오프셋 페이징이 수 초씩 걸리며 장애를 유발하는 진짜 원인은 **물리적인 디스크 I/O** 때문이다.

```
[MySQL InnoDB의 2만 건 오프셋 조회]
디스크의 16KB 데이터 블록(Page)들을 버퍼 풀(Buffer Pool)로 퍼올림
➜ 엄청난 디스크 Random I/O 발생
➜ 기존 캐시된 데이터가 버퍼 풀에서 밀려남 (Cache Churning)
➜ 수 초 소요!

[H2 인메모리의 2만 건 오프셋 조회]
2만 건 전체가 이미 RAM(힙 메모리)에 로드되어 있음
➜ 디스크 I/O = 0
➜ CPU가 메모리 주소 2만 개를 순차 순회(for문 스킵)
➜ 0.08ms 만에 완료!
```

H2 인메모리 데이터베이스는 디스크 I/O라는 가장 거대한 병목 구간이 완전히 생략되어 있다. RAM에서 20,000건의 행 포인터를 순회하는 것은 현대 CPU에게 눈 깜짝할 사이에 끝나는 가벼운 작업이다.

결국 **"디스크 병목을 재현할 수 없는 인메모리 환경"**에서 디스크 병목을 측정하려 했으니, 실무 환경과 완전히 동떨어진 마이크로초 단위의 노이즈만 측정되었던 것이다.

## 3. 수치(ms)를 버리고 실행 계획(`EXPLAIN`)을 보라

그렇다면 이 벤치마크는 무의미했던 것일까? 그렇지 않다.  
의미 있는 답은 소요 시간 수치가 아니라 **실행 계획(`EXPLAIN`)** 속에 숨어 있었다.

### 오프셋 방식 실행 계획
```sql
SELECT "ID", "TITLE" FROM "PUBLIC"."TODO"
WHERE "USER_ID" = ?1 
ORDER BY 1 
OFFSET 19980 ROWS FETCH NEXT 20 ROWS ONLY;
```
실행 계획을 보면 인덱스를 타더라도 엔진이 `19980`번 카운터를 올리며 **앞선 19,980건을 메모리에서 모두 읽고 버리는(Fetch & Discard)** 알고리즘을 수행한다. 데이터가 2만 건이 아니라 2천만 건이라면 이 스캔 비용은 파멸적이다.

### 커서 방식 실행 계획
```sql
SELECT "ID", "TITLE" FROM "PUBLIC"."TODO"
WHERE ("USER_ID" = ?1) AND ("ID" > ?2) 
ORDER BY 1 
FETCH FIRST 20 ROWS ONLY;
```
커서 방식은 `("ID" > ?2)` 조건이 인덱스의 시작 위치(Seek Key) 역할을 한다. 엔진은 B-Tree를 타고 19,980 위치로 단숨에 수직 점프한 뒤, **정확히 요청된 첫 20건(`FETCH FIRST 20 ROWS ONLY`)만 읽고 즉시 쿼리를 종료(Early Termination)**한다.

비록 H2 메모리 상에서는 두 작업의 차이가 0.06ms에 불과했지만, **스토리지 엔진이 행을 읽어들이는 알고리즘적 구조는 $O(N)$과 $O(1)$의 하늘과 땅 차이**였던 것이다.

---

## 4. 이번 실험을 통해 얻은 3가지 교훈

1. **마이크로 벤치마크의 소요 시간(ms)을 맹신하지 말라**:
   - 단위 테스트나 인메모리 환경에서 수십 마이크로초 단위로 측정되는 시간은 JVM 상태와 머신 노이즈에 의해 쉽게 뒤집힌다. 정밀 측정이 필요하다면 JMH(Java Microbenchmark Harness) 같은 전문 도구를 사용해 수만 번의 웜업을 거쳐야 한다.
2. **테스트 환경의 물리적 특성을 이해하라**:
   - 인메모리 DB(H2)는 비즈니스 로직과 SQL 문법의 정합성을 검증하기 위한 도구이지, 물리적 디스크 I/O와 버퍼 풀 경합을 시뮬레이션하는 성능 벤치마크 도구가 아니다.
3. **숫자 너머의 알고리즘과 실행 계획을 신뢰하라**:
   - 벤치마크 수치가 3배든 1.2배든, 중요한 것은 `EXPLAIN`으로 확인한 **스토리지 엔진의 순회 구조**다. Fetch & Discard를 유발하는 쿼리는 데이터가 늘어나는 순간 반드시 프로덕션 장애의 뇌관이 된다.
