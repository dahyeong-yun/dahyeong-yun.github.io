## 들어가며

"데이터베이스 기본키(PK)로 `1, 2, 3...` 순차적으로 증가하는 시퀀셜 키(Auto-Increment)를 쓰면 URL이나 API에서 남의 데이터를 쉽게 털어갈 수 있지 않나요?"

신규 프로젝트의 데이터 모델링을 할 때 종종 나오는 질문이다. 결론부터 말하자면 **맞다. 매우 치명적인 보안 취약점이 될 수 있다.**

하지만 실제 수많은 서비스의 데이터베이스를 열어보면 여전히 압도적인 비율로 `BIGINT AUTO_INCREMENT`가 쓰이고 있다. 개발자들이 보안에 무감각해서일까? 그렇지 않다. 여기에는 데이터베이스 엔진의 물리적 저장 구조와 **쓰기 성능**이라는 거대한 현실적 장벽이 숨어있다.

이번 글에서는 시퀀셜 키가 초래하는 실제 보안 위협을 살펴보고, 왜 포기하기 어려운지, 그리고 실무에서는 성능과 보안이라는 두 마리 토끼를 어떻게 잡고 있는지 정리해 본다.

---

## 1. 순차 키가 부르는 3가지 보안 재앙

DB의 순차 키를 REST API의 식별자로 그대로 노출(`GET /orders/1004`)할 때 맞닥뜨리는 위협은 크게 세 가지다.

### ① IDOR: 1만 바꿨을 뿐인데 남의 정보가 보인다
보안 취약점 중 가장 흔하고 위험한 것이 바로 **IDOR(Insecure Direct Object Reference)**다.

내 주문 내역 URL이 `/orders/1004`라면, 누구나 호기심에 `/orders/1003`을 입력해 볼 수 있다. 만약 백엔드 코드에서 "이 주문이 현재 로그인한 사용자의 주문인가?"를 검증하는 권한 체크(인가)를 단 한 줄이라도 빠뜨렸다면, 남의 배송지 주소, 결제 금액, 개인정보가 고스란히 화면에 뜬다.

### ② 독일 탱크 문제: 회사의 매출이 실시간 생중계된다
권한 체크를 꼼꼼히 해서 남의 주문 데이터를 볼 수 없게 막았다고 안심할 수 있을까? 그렇지 않다. **숫자 자체가 주는 메트릭 정보**가 유출된다.

2차 세계대전 당시 연합군은 독일군 탱크의 일련번호를 통계학적으로 분석해 한 달 탱크 생산량을 정확히 맞췄다(이를 통계학에서 '독일 탱크 문제'라 부른다).

```
1월 1일 가입 시 내 회원 번호: 10,000
1월 31일 가입 시 내 부계정 회원 번호: 10,500
→ "아, 이 회사는 한 달 신규 가입자가 딱 500명이구나."
```

경쟁사나 투자자가 매일 상품을 하나씩 결제해 보며 주문 번호의 차이를 계산하면, 회사의 일일 주문 건수와 대략적인 매출 규모를 실시간으로 손바닥 들여다보듯 파악할 수 있다.

### ③ 전수 스크래핑
공개 게시판이나 상품 데이터의 경우, `1`부터 `1000000`까지 루프를 돌려 요청을 쏘면 단 한 건의 누락도 없이 데이터베이스의 전 데이터를 완벽하게 긁어갈 수 있다.

## 2. 그런데 왜 다들 시퀀셜 키를 포기하지 못할까?

이토록 명확한 위험이 있는데도 왜 다들 무작위 난수인 `UUID v4`를 쓰지 않고 시퀀셜 키를 고집할까? 이유는 **RDBMS의 B-Tree 인덱스 동작 원리** 때문이다.

MySQL(InnoDB) 같은 RDBMS는 기본키(PK)를 기준으로 디스크의 16KB짜리 '페이지(Page)'라는 블록에 데이터를 정렬하여 저장한다([[database-primary-key-strategies|B-Tree 클러스터드 인덱스]]).

* **순차 키(Auto-Increment)**: 새로운 행이 들어올 때마다 항상 디스크 맨 마지막 페이지의 빈자리에 순서대로 착착 달라붙는다(Append-only). 디스크 I/O가 순차적으로 일어나며 극상의 쓰기 속도를 낸다.
* **무작위 난수(UUID v4)**: `a8098c...` 다음에 `12f801...`이 들어온다. 이미 꽉 차서 닫혀 있는 과거의 페이지 중간을 비집고 들어가야 한다.

```
[기존 꽉 찬 페이지] 
  → 중간에 무작위 UUID 삽입 시도!
  → 디스크 블록을 둘로 쪼개는 "Page Split" 발생
  → 불필요한 디스크 I/O 폭증 + 메모리 단편화 발생
```

데이터가 몇만 건일 때는 체감되지 않지만, 수백만~수천만 건이 쌓이는 순간 UUID v4를 PK로 쓴 테이블은 디스크 I/O 병목으로 인해 쓰기 성능이 바닥으로 곤두박질친다.

## 3. 실무에서는 어떻게 해결할까?

성능(순차 정렬)과 보안(유추 불가능)은 양립할 수 없는 것처럼 보인다. 하지만 실무 아키텍처에서는 이를 매우 영리하게 해결한다.

### 해법 1. Public ID 패턴 (가장 널리 쓰이는 하이브리드)

Stripe, 토스, 쿠팡 등 수많은 테크 기업들이 채택하고 있는 방식이다. **키를 2개** 둔다.

```sql
CREATE TABLE orders (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY, -- DB 내부용 (초고속 조인 및 쓰기용)
    public_id  VARCHAR(32) NOT NULL UNIQUE,       -- 외부 노출용 (URL, API용)
    user_id    BIGINT NOT NULL,
    amount     INT NOT NULL
);
```

1. **DB 내부**: 테이블 간의 외래키(FK) 조인과 클러스터드 인덱스는 가볍고 빠른 8바이트 `id`를 사용한다.
2. **외부 노출**: 프론트엔드나 REST API에는 `public_id`(예: `ord_9xK8mP2a` 같은 NanoID 또는 UUID)만 보여준다.
   * `GET /api/v1/orders/ord_9xK8mP2a`

이렇게 하면 외부 사용자는 다음 주문 번호를 절대 유추할 수 없으면서도, DB 내부에서는 여전히 순차 정렬의 초고속 쓰기 성능을 온전히 누릴 수 있다.

### 해법 2. 차세대 표준, UUID v7의 도입

최근 신규 마이크로서비스(MSA)를 설계한다면 테이블에 키를 2개 두는 대신 **UUID v7**을 단일 PK로 채택하는 사례가 급증하고 있다. (2024년 RFC 9562로 정식 표준화되었다.)

* **앞부분**: 밀리초(ms) 단위의 **타임스탬프** $\rightarrow$ 시간순으로 정렬되므로 B-Tree Page Split이 발생하지 않음!
* **뒷부분**: 강력한 **의사 난수(Random Bits)** $\rightarrow$ 1씩 증가하는 숫자가 아니므로 다음 번호를 유추할 수 없음!

키 하나로 순차 쓰기 성능과 유추 불가능성을 한 번에 해결할 수 있는 훌륭한 대안이다.

## 4. 잊지 말아야 할 본질: "식별"은 "인가"가 아니다

아무리 복잡한 난수 ID를 도입하더라도 반드시 명심해야 할 원칙이 있다.

> **"키를 어렵게 만드는 것은 인가(Authorization)를 대신할 수 없다."**

공격자가 피싱이나 네트워크 패킷 감청을 통해 우연히 타인의 `public_id`(`ord_9xK8mP2a`)를 손에 넣었을 수도 있다. 이때 백엔드 애플리케이션에서 다음과 같이 조회하고 있다면 여전히 뚫린다.

```python
# 취약한 코드: ID만 맞으면 무조건 조회해 줌
order = db.query(Order).filter(Order.public_id == public_id).first()
```

반드시 현재 로그인한 사용자의 세션 정보와 대조하는 소유권 검증이 코드 레벨에서 선행되어야 한다.

```python
# 안전한 코드: 식별자와 소유자를 항상 함께 검증
order = db.query(Order).filter(
    Order.public_id == public_id,
    Order.user_id == current_user.id
).first()
```

## 마치며

* 시퀀셜 키를 외부에 그대로 노출하면 **IDOR, 비즈니스 지표 유출, 스크래핑**에 노출되는 것이 맞다.
* 그럼에도 시퀀셜 키를 쓰는 이유는 RDBMS **B-Tree 인덱스의 페이지 분할(Page Split)을 막고 쓰기 성능을 지키기 위함**이다.
* 따라서 대규모 실무 환경에서는 **내부 조인용 PK(`BIGINT`)와 외부 노출용 식별자(`public_id`)를 분리**하거나, **UUID v7**을 도입하여 성능과 보안의 균형을 잡는다.
* 그리고 어떤 키를 쓰든, **소유권 검증(인가 로직)**은 백엔드 엔지니어의 절대적인 기본기다.
