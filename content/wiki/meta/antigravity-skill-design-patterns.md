Google Antigravity(AGY)의 **스킬(Skill)**은 에이전트에게 정교한 다단계 절차와 도메인 런북을 주입하는 핵심 커스터마이징 단위다. 

단순히 프롬프트를 길게 적는 것을 넘어, 토큰 컨텍스트를 절약하고 어떤 프로젝트 디렉토리에서도 안정적으로 동작하는 고품질 스킬을 만들기 위한 설계 패턴들을 정리한다.

---

## 1. 안티그래비티 스킬의 3대 설계 원칙

### ① 점진적 공개 (Progressive Disclosure)
* **문제**: 수많은 지침과 매뉴얼을 시스템 프롬프트에 통째로 넣으면 컨텍스트 윈도우가 낭비되고 모델의 추론 집중력이 떨어진다.
* **해결**:
  - 시스템 초기 부팅 시에는 `SKILL.md`의 **`name`과 `description`**만 노출한다.
  - 모델이 사용자 발화를 분석하여 해당 스킬이 필요하다고 판단했을 때만 본문 전체를 동적으로 읽어온다.
  - 본문이 너무 길어질 경우 방대한 레퍼런스는 `references/` 하위 파일로 분리하고 상대 경로 링크로 참조한다.

### ② 3인칭 명시적 트리거 Description
`SKILL.md`의 Frontmatter에서 가장 중요한 필드는 `description`이다.
* 3인칭으로 서술하며, **스킬이 무엇을 하는지(What)**와 함께 **사용자가 어떤 말을 할 때 호출해야 하는지(When)**를 명시적인 예시 발화("~해줘", "~정리해줘")와 함께 기재한다.

### ③ 절차의 결정성 (Determinism)과 군더더기 배제 (No Duplication)
* 모델이 이미 알고 있는 일반적인 프로그래밍 지식은 과감히 생략하고, 해당 워크플로우에 특화된 고유한 절차와 분기 조건에 집중한다.
* 모호한 표현("적절히 처리한다") 대신 구체적인 우선순위 규칙과 검증 절차를 명시한다.

## 2. 실전 아키텍처 패턴

### 패턴 A: 2단계 파이프라인 패턴 (Human-in-the-Loop)

```
[ Phase 1: 분석 및 기획 제안 ] ──(표/목록 제시)──> [ 🛑 사용자 확인 및 피드백 대기 ]
                                                            │
                                                            ▼ (승인)
                                                   [ Phase 2: 실행 및 파일 생성 ]
```

* **적용처**: 대화 내용을 분석해 문서를 작성하거나, 리팩토링 계획을 수립할 때.
* **이유**: AI가 스스로 판단하여 즉시 파일들을 생성해버리면, 잘못 분류되거나 불필요한 파일이 만들어졌을 때 롤백하고 재작성하는 비용이 훨씬 크다.
* **설계 지침**:
  - Phase 1에서 분류 결과, 저장 경로, 작업 개요를 표 형태로 제안하고 **명시적으로 실행을 멈추고(Stop & Wait) 사용자의 승인을 요구**한다.
  - 사용자가 확인하거나 수정한 뒤에만 Phase 2(실제 쓰기 작업)로 이행한다.
  - 단, 사용자가 처음부터 *"알아서 바로 생성해줘"*라고 지시한 경우에 한해 즉시 일괄 실행하는 우회로를 열어둔다.

### 패턴 B: 계층형 환경 탐색 패턴 (Hierarchical Resolution & Fallback)

* **문제**: 에이전트가 옵시디언 볼트가 아닌 일반 백엔드 소스코드 저장소(예: 스프링 부트 프로젝트)에서 대화 중일 때, 상대 경로로 문서를 생성하면 소스 저장소에 문서가 흩어지거나 에러가 발생한다.
* **해결**: 대상 저장소 경로를 3단계 계층 구조로 탐색한다.

```
1순위 (현재 작업 디렉토리): CWD가 볼트 구조(.obsidian/, content/wiki/ 등)를 갖추었는가?
         │ [No]
         ▼
2순위 (설정/환경변수): OBSIDIAN_VAULT_PATH 등 명시적 전역 설정이 있는가?
         │ [No]
         ▼
3순위 (Known Vaults Fallback): 사용자의 대표적인 로컬 볼트 목록을 순차 탐색
         • ~/Repositories/.../publish/dahyeong-yun.github.io
         • ~/Repositories/.../obsidian-para
         ➜ 실제로 존재하는 경로를 찾아 타겟으로 자동 확정!
```

* **장점**: 개발자가 어디서 작업하든 마치 하드코딩된 것처럼 사용자의 메인 볼트를 찾아가며, 설정 파일이나 제안 단계 피드백을 통해 언제든 대상을 바꿀 수 있는 유연성을 확보한다.

### 패턴 C: 안전한 상태 강제 (Draft-First)
* 마크다운 문서나 블로그 포스트를 생성하는 스킬은 Frontmatter에 무조건 **`draft: true`**를 기본값으로 주입하도록 강제한다.
* 미완성 초안이 정적 사이트 빌드나 배포 파이프라인에 실수로 포함되는 문제를 원천 차단한다.

## 3. 커스텀 요소 선택 가이드

| 상황 / 요구사항 | 추천 방식 | 이유 |
| :--- | :---: | :--- |
| 프로젝트 전반에 걸쳐 항상 지켜야 하는 코딩 컨벤션, 아키텍처 금지 규칙 | **Rule** (`.agents/rules/*.md`) | 컨텍스트 스위칭 없이 모든 턴에 상시 적용되어야 함 |
| 특정 요청 시에만 발동하는 다단계 작업 절차 (문서 초안화, 배포 런북, 백업) | **Skill** (`skills/<name>/SKILL.md`) | 필요할 때만 호출되어 컨텍스트 윈도우를 아낄 수 있음 |
| 대규모 리팩토링이나 여러 문서의 동시 작성으로 메인 컨텍스트가 무거워질 때 | **Subagent** (`invoke_subagent`) | 독립된 작업 공간과 컨텍스트를 할당하여 병렬 실행 및 메인 토큰 보호 |
| 도메인 모델, 공통 에러코드 매핑 테이블 등 참조용 정적 지식 | **Skill Resource** (`resources/`, `references/`) | 스킬 본문이 필요로 할 때만 부분적으로 열람 |
